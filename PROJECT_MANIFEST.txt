REPOSITORY LAYOUT single repository, no submodules

-------------------------------------------------------------------------------
 DESCRIPTION
-------------------------------------------------------------------------------
A lightweight offline Linux music player with broad audio-format support,
metadata handling, playlists, queue management, library scanning, artwork,
search, and a desktop-oriented web interface.

Independent project. Inspired by the usability and information density of
desktop music players such as Tauon Music Box. Not affiliated with Tauon,
not a fork of it, and shares no code with it.

-------------------------------------------------------------------------------
 DEPENDENCIES
-------------------------------------------------------------------------------
REQUIRED (Python packages): NONE.
  Harmonia runs entirely on the Python standard library.

REQUIRED (system):
  python3            >= 3.10
  ffmpeg + ffprobe   audio decoding; without it nothing plays
  SQLite with FTS5   bundled with CPython on mainstream distros
  libasound (ALSA)   audio output

OPTIONAL (each degrades gracefully, and the program reports what is missing):
  python-dbus-next   MPRIS, media keys, playerctl
  numpy              faster volume/ReplayGain scaling (falls back to audioop)
  gtk4 + libadwaita + python-gobject   native GTK front-end

-------------------------------------------------------------------------------
 SUPPORTED AUDIO FORMATS
-------------------------------------------------------------------------------
Fully implemented AND decode-tested end-to-end (tag parsing + PCM output
length checked against expected duration):

  MP3        CBR and VBR   ID3v2.2/2.3/2.4 + ID3v1
  FLAC                     Vorbis comments, STREAMINFO, PICTURE
  WAV        RIFF          LIST/INFO and embedded 'id3 ' chunk
  Ogg Vorbis               Vorbis comments
  Opus       Ogg           OpusTags
  AAC / M4A  MP4           iTunes-style ilst atoms
  AIFF/AIFC  IFF           'ID3 ' chunk, NAME/AUTH

Detected but NOT decode-tested (no fixture was generated):
  ALAC (Apple Lossless) - metadata parser handles it; decode should work
  via ffmpeg but is unverified.

Plays but tags not natively parsed:
  Anything else the local ffmpeg build decodes (WavPack, Musepack, WMA, APE,
  DSF, ...). These fall back to ffprobe for audio properties and use the
  filename as the title. Check your build with: ffmpeg -decoders

NOT supported:
  DRM-protected files (iTunes .m4p).
  Tracker/chiptune formats needing a dedicated playback engine, not a decoder.

High-resolution audio: 24-bit and 96/192 kHz files decode at their native
rate and channel count; they are not downsampled to 44.1 kHz.

-------------------------------------------------------------------------------
 FEATURES ACTUALLY IMPLEMENTED
-------------------------------------------------------------------------------
Playback engine
  play, pause, resume, stop, next, previous, seek
  volume, mute, per-track ReplayGain
  shuffle, repeat off/all/one
  queue with add, play-next, remove, reorder, clear, save-as-playlist
  gapless playback when consecutive tracks share format
  resume position and queue restored across restarts
  error recovery: corrupt/missing/unsupported files are skipped, not fatal

Metadata
  title, artist, album, album artist, track no., disc no., genre, date,
  composer, comment, compilation flag, ReplayGain tags, MusicBrainz track ID
  embedded metadata kept strictly separate from library metadata
  audio files are opened read-only and NEVER written to

Library
  add/remove/rescan folders; nested directories
  incremental scanning via (mtime, size) fingerprint
  detects new, modified and deleted files
  automatic detection of filesystem changes (inotify, polling fallback)
  SQLite database with schema versioning via PRAGMA user_version

Search
  FTS5 full-text over title, artist, album, album artist, genre, filename
  prefix matching, debounced search-as-you-type
  malformed query input falls back to LIKE instead of erroring

Cover art
  embedded artwork first, then folder art (cover/folder/album/front .jpg/.png)
  content-hashed disk cache; missing artwork handled gracefully

Interface
  album grid, album detail, artist list, track list, genre list
  favorites, recently played, recently added, playlists, queue panel
  persistent player bar with artwork, seek, times, format badge
  right-click context menus (play, play next, queue, favorite, add to
  playlist, view metadata, open folder, remove from library)
  keyboard shortcuts; dark and light themes (separate palettes, not inverted)
  virtualized lists + server-side paging for large libraries
  settings page with folders, theme, ReplayGain, resume

Desktop integration
  MPRIS2 D-Bus interface (implemented; see untested section)
  .desktop launcher entry

-------------------------------------------------------------------------------
 FEATURES THAT COULD *NOT* BE TESTED IN THE SANDBOX
-------------------------------------------------------------------------------
These are unverified. They are listed plainly because a first user deserves
to know where the risk is.

1. AUDIBLE AUDIO OUTPUT - NEVER VERIFIED.
   The build machine has no sound card at all (/dev/snd does not exist).
   Decoding is proven exact: a 2-second FLAC produces exactly 176,400 PCM
   bytes; a VBR MP3 matches ffprobe to 5.041633 s. But NO AUDIO HAS EVER
   BEEN HEARD FROM THIS PROGRAM. AlsaSink is real ctypes code that
   correctly raises a catchable error in the sandbox and has never written
   a byte to a real device. THIS IS THE MOST LIKELY PLACE FOR A BUG.

2. MPRIS / MEDIA KEYS - NEVER EXECUTED.
   No D-Bus session bus and no dbus-next package (no network access to
   install one). The code is written against the MPRIS2 spec and reports
   its own unavailability honestly rather than faking success. Verify with
   `playerctl status` after installing python-dbus-next.

3. GTK4 FRONT-END - NEVER RUN.
   No GTK4, libadwaita or PyGObject available. harmonia_gtk.py byte-compiles
   and exits with a helpful message when GTK is absent, but it is a port
   skeleton, not verified code. The web interface is the tested front-end.

4. ALAC DECODING - UNTESTED. No fixture generated.

5. 50,000+ TRACK LIBRARIES - UNTESTED. 20,000 was measured. Server-side
   paging makes per-view cost flat in library size, but 50,000 was not
   run and is therefore not claimed.

6. REAL-WORLD TAG VARIETY - PARTIALLY TESTED. Fixtures are ffmpeg-produced
   and therefore well-formed. Unusual or broken taggers may expose gaps.
   Parsers record warnings and return partial data rather than raising,
   and those warnings are shown in the metadata dialog.

7. NON-x86 ARCHITECTURES - UNTESTED. Nothing is architecture-specific
   (pure Python + ctypes + ffmpeg), but no ARM/Raspberry Pi run happened.

8. MULTI-USER / PERMISSION EDGE CASES - PARTIALLY TESTED. Unreadable
   directories are skipped during scanning (tested), but running as a
   restricted user against a shared library was not exercised.

-------------------------------------------------------------------------------
 KNOWN LIMITATIONS (design, not bugs)
-------------------------------------------------------------------------------
- Gapless(still in progress)
  playback works only when consecutive tracks share sample rate and
  channel count. A format change forces an ALSA device reconfigure and a
  short gap. This is a hardware constraint, not a shortcut.
- Encoder delay is not compensated. MP3/AAC gapless is close but not
  sample-exact. FLAC, WAV and AIFF are exact.
- ReplayGain applies TRACK gain only. Album gain is parsed and stored but
  not yet applied.
- No tag editor. Deliberate: nothing writes to audio files, so there was no
  safe path to a half-built editor.
- The interface runs over loopback HTTP (127.0.0.1). It is not a network
  service, but on a shared machine another local user could reach the port.
  Do not pass --host 0.0.0.0.
- No online metadata lookup, no telemetry, no account, no internet required.

-------------------------------------------------------------------------------
 DATA SAFETY
-------------------------------------------------------------------------------
- Music files are opened 'rb'. Nothing writes to them, ever.
- "Remove from library" deletes a database row. It never deletes a file.
- Database and artwork cache live in $XDG_DATA_HOME/harmonia
  (default ~/.local/share/harmonia). No paths are hard-coded to a home dir.
- Cover art is served only from inside the cache directory; paths outside
  it are rejected.
- Opening a containing folder uses a list-form subprocess call, so filenames
  with quotes or spaces cannot be injected into a shell.
- Test fixtures are synthetic sine tones generated by ffmpeg. No copyrighted
  audio is used or distributed.
